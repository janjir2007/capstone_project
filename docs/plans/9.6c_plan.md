## 1. Before anything: check the login flow Artlab gave matches the code

Our client logs in with `POST {ARTLAB_URL}/auth/login` and body `{username, password, type: "api"}`. The token comes back
in the `Authorization` response header (`src/artlab/client.py`, `login()`). This flow was only checked on the **test** account.

Ari compares the token endpoint in Artlab's message with that flow. He does **not** share the credentials, only
"same / different":
- **Same** (`/auth/login`, `type: api`) → go on.
- **Different** (other path, `client_id/secret`, a fixed token, etc.) → **STOP.** That needs a client change
  (added to 9.6c-2). We must never ask for a non-expiring token (artlab_api_notes §1, RISK-22).

## 2. Settings: what Ari adds to the server `.env`

Exact names (from `.env.prod.example`, read by `docker-compose.prod.yml` → service `artlab-sync` only):

| Name | Value | When |
|---|---|---|
| `ARTLAB_URL` | `https://api.artlab.mn/v2` (no trailing `/`; the code strips it anyway) | now |

**Watch out: the server `.env` may already hold empty `ARTLAB_*=` lines** if it was copied from `.env.prod.example`.
Appending a second `ARTLAB_URL=` would leave two lines with the same name (which one compose uses: *needs verification*).
So check first, and print only the names, never the values:

```
cd ~/oil-change-predictor
grep -o '^ARTLAB_[A-Z_]*=' .env          # names only
```

- No lines printed → append. `cat >> .env`, type the three lines, then Ctrl-D. Typed lines do not go into shell history,
  but `echo '…' >> .env` would.
- Lines printed → fill them in with `nano .env` instead of appending.
- If the password has `$`, `#`, a space or quotes, wrap it in single quotes: `ARTLAB_PASS='…'`. How compose treats
  `$` in `.env` values: *needs verification*. The length check below catches a mangled value.
- `chmod 600 .env`

**Proof that only the sync container gets them** (each command prints names and lengths, never values):

```
# sync container: expect ARTLAB_URL 24, and the user/password lengths Ari knows
docker compose -f docker-compose.prod.yml --profile sync run --rm --no-deps -T artlab-sync \
  python -c "import os; print({k: len(v) for k, v in sorted(os.environ.items()) if k.startswith('ARTLAB_')})"

# web API: expect []
docker compose -f docker-compose.prod.yml exec -T api \
  python -c "import os; print(sorted(k for k in os.environ if k.startswith('ARTLAB_')))"
```

Why the API never gets them (RISK-22, D-133):
- The `api` service in `docker-compose.prod.yml` lists its environment one key at a time and has **no `env_file:`**. No `ARTLAB_*` key is listed.
- `.dockerignore` keeps `.env` and `.env.*` out of every image. The API container only mounts `./models`, so it cannot read the file either.
- `artlab-sync` sits under `profiles: ["sync"]`, so `up -d` never starts it.
- `tests/test_deploy.py::test_artlab_credentials_only_in_the_sync_service` fails CI if any other service gets an `ARTLAB_*` key.
- Adding the lines needs **no** restart. `api`/`ui` do not use them, so no `--force-recreate`.

## 3. Running the probe

### 3.1 Commands (server, in `~/oil-change-predictor`)

The output goes to `/root/artlab_probe/`, which is outside the repo, so it can never be committed.

```
mkdir -p /root/artlab_probe && chmod 700 /root/artlab_probe
P="docker compose -f docker-compose.prod.yml --profile sync run --rm --no-deps -T artlab-sync python -m scripts.artlab_probe"

# 0. the image has the probe (no login, no network)
$P --help

# 1. NOW (safe): login + payment methods
$P --section paymethods > /root/artlab_probe/01_paymethods.json

# 2. AFTER 9.6c-2 is deployed: bills, short window first, then 30 days
$P --section bills --from <today-7> --to <today> > /root/artlab_probe/02_bills_7d.json
$P --section bills --from <today-30> --to <today> > /root/artlab_probe/03_bills_30d.json

# 3. ONLY when the accountant gives the account code(s), AFTER 9.6c-2:
$P --section acc-txn --account <code> --from <today-30> --to <today> > /root/artlab_probe/04_acctxn.json
```

Notes:
- `--no-deps`: the probe never touches our database, so the run does not wait for `db`.
- `-T`: no terminal, so the JSON goes into the file cleanly.
- `--section all` (the default) is **not** used. Each section runs on its own so that each file is small and gets its own review.
- Size: `fetch_all` stops at 20 pages × 500 = 10,000 bills and prints `"truncated": true`. If 30 days come back truncated, use 7-day windows.
- With a 0.3 s pause per request, a 30-day bills run makes a few dozen requests and finishes in seconds.

## 4. Match rate plates ↔ bills: what we can and cannot learn now

- **Now (bills section, after G4/G5):** the **extraction rate**. For completed oil-change sales, we count how many
  descriptions hold a valid plate (`find_plates` → `normalize_plate` + `is_valid_plate`), a phone, both, or
  neither. That rate is the **upper limit** of matching. If it is low, the oil changer is not typing plate + phone
  into the receipt as assumed (artlab_api_notes §8), and that has to be fixed in practice before any sync.
- **Not now:** a real match rate (bill → our service). Our database holds **demo data until the demo wipe (9.8)**. Matching
  real bills against synthetic trucks measures nothing, and a phone could collide by chance.
- **Later (optional item in 9.6c-2, PM decides):** `--section match`. It loads services with the existing read-only
  `load_candidates()` SELECT, runs `src/artlab/matching.py` in memory, and prints only the confidence counts
  (both / plate / phone / none / multiple / conflict). It **writes nothing**. It is only meaningful 2+ weeks after 9.8.
  It needs `db` (no `--no-deps`) and the `POSTGRES_*` values, which `artlab-sync` already has.

## 5. Why writes are impossible from our side

Every request the probe can send:

| Method | Path | Section |
|---|---|---|
| POST | `/auth/login` (fixed body: username, password, `type: "api"`) | all |
| GET | `/auth/check`, `/auth/connections` | bills |
| GET | `/pos/bills`, `/pos/bills/types`, `/pos/bills/statuses` | bills |
| GET | `/invoices` | bills |
| GET | `/pos/paymethods`, `/pos/paymethods/types` | paymethods |
| POST | `/report/acc-txn` (fixed body: `accountCodes` digits only, `startDate`, `endDate`; Artlab confirmed read-only) | acc-txn, only with `--account` |

How it is enforced (`src/artlab/client.py`):
- `get()` refuses any path that is not in the frozen `READ_PATHS` set and raises `NotAllowedError` **before** sending.
- The client has **no** generic POST/PUT/PATCH/DELETE method. The only two POSTs build their own body from fixed keys.
- Tests: `test_get_outside_allow_list_is_refused_before_sending`, `test_client_has_no_generic_post`,
  `test_acc_txn_body_has_exactly_three_keys`, `test_acc_txn_rejects_bad_input_before_sending`,
  `test_only_post_ever_sent_is_login` (a full bills run sends no POST except login).

**Still open (RISK-22):** Artlab has not confirmed that the api user is read-only. Our code cannot write, but the
credentials might be able to. Ask Artlab (Ari/PM) to confirm and, if possible, restrict it. Until then the
credentials stay in the server `.env` only, and nobody types them anywhere else (no Postman on the Mac).

## 7. What we learn about bank account codes and credit = LOAN

**Credit = LOAN.** From `paymethods` (run 1):
- Is there a method with `type: LOAN` (test DB: id 4 «Зээл»)? What is its name? Are there other credit-like methods?
- From `bills` (run 2/3): how many bills in the window carry a `LOAN` payment, and how many sales have **0 payments**
  (status «Тодорхойгүй» in `src/artlab/status.py`).
- What it cannot prove: that Geo-Expert's credit sales **always** use LOAN. Only the accountant can confirm that
  (PROJECT_STATE §4). If LOAN is missing or the count is 0 over 30 days, ask the accountant how credit sales are recorded.

**Bank account codes.** The probe **cannot discover them**. No allow-listed read-only endpoint lists accounts
(trial balance would, but it is not on the list, artlab_api_notes §8c). What the probe can do once the accountant
gives the code(s):
- Show the acc-txn **row fields** (id / date / amount / sign / description). These are needed to write the transfer
  parser (9.6b-T), and it has been blocked on them since 9.6b-1.
- Show whether the descriptions carry plates/phones (counts only).
- Caveat: **a wrong code also returns 200 with an empty list** (test DB, artlab_api_notes §8c). "0 rows" proves
  nothing. A code is confirmed only when rows come back for a period in which the accountant knows transfers happened.
