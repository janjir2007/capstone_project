### 2a. Can the token be limited to one folder? (checked 2026-11-06, sources below)

| Option | What the docs say | Usable? |
|---|---|---|
| rclone `access_scopes` | rclone lets you choose the scopes it requests. Default: `Files.Read Files.ReadWrite Files.Read.All Files.ReadWrite.All Sites.Read.All offline_access`. Documented preset without SharePoint: `Files.Read Files.ReadWrite Files.Read.All Files.ReadWrite.All offline_access`. A custom space-separated list is allowed. [rclone OneDrive docs, "--onedrive-access-scopes"] Added in rclone v1.59.0 (maintainer comment in [issue #5826](https://github.com/rclone/rclone/issues/5826)). | **Yes**, narrows the token, but not to one folder (next row) |
| Drop the `.All` scopes, keep `Files.Read Files.ReadWrite` | Microsoft: `Files.ReadWrite` = "read, create, update and delete the signed-in user's files"; `Files.ReadWrite.All` = "… all files the signed-in user can access". **But for personal Microsoft accounts, Microsoft notes that `Files.Read` / `Files.ReadWrite` also grant access to files shared with the signed-in user.** [Graph permissions reference] | **Yes**, smallest scope we can use. It drops SharePoint browsing (`Sites.Read.All`) and the `.All` scopes. It does **not** stop access to Ari's whole OneDrive, and on a personal account it does **not** block the boss's shared folders either |
| App folder (`Files.ReadWrite.AppFolder`) | Microsoft: gives read/write **only** to the app's own folder `Apps/<app name>`, addressed as `/drive/special/approot`; listed as **preview**; supports personal accounts. [App Folder concept page, Graph permissions reference] | **No, not with rclone today.** [Issue #5826](https://github.com/rclone/rclone/issues/5826) "Support OneDrive AppFolder" is **open**: rclone builds requests from item IDs, and the reporter found that AppFolder-scoped requests do not accept them (2022-09-15, still open 2024-06-08). It would also need an own Azure app (the folder is named after the app), and it could not use the existing GeoExpert-Backups folder |
| Folder-only scope for a chosen folder (`Files.SelectedOperations.Selected`, `Files.ReadWrite.Selected`) | `Files.ReadWrite.Selected` is "only valid on work or school accounts"; `Files.SelectedOperations.Selected` is set up in "SharePoint Online or OneDrive", with no note that it supports personal accounts. [Graph permissions reference] | **No** for a personal account / not supported by rclone (not in rclone's docs) |
| rclone `root_folder_id` | "ID of the root folder … in special circumstances you might know the folder ID that you wish to access", "isn't normally needed". [rclone OneDrive docs] | **Yes, as a software fence** (below). It changes what rclone *uses* as its root, **not** what the token *may* do |

**Result: a folder-only token is not possible** for this setup (personal account + rclone). We use:

1. **Smallest working scope:** `access_scopes = Files.Read Files.ReadWrite offline_access`
   (`offline_access` = refresh token so the nightly job keeps working). That this list is enough for
   rclone's config + upload + list + delete on OneDrive Personal is **NEEDS VERIFICATION** in setup
   step 5. If rclone fails with it, use the documented preset without SharePoint
   (`Files.Read Files.ReadWrite Files.Read.All Files.ReadWrite.All offline_access`) and note that in
   the STEP 2 handoff.
2. **Software fence to the folder** (what rclone actually touches):
   - the remote `ocp-offsite` gets `root_folder_id = <ID of GeoExpert-Backups>`, so `ocp-offsite:` *is*
     that folder (setup step 5b). **NEEDS VERIFICATION** that root_folder_id works on OneDrive
     Personal: after setting it, `rclone lsf ocp-offsite:` must list only the folder's contents;
   - the script's remote path is a **constant** `ocp-offsite:db` (no env override), every rclone call
     uses a path under it, and the script stops if `rclone.conf` has no `root_folder_id` line for
     `ocp-offsite` (it reads only that one key, never prints the file);
   - shared folders: rclone does not support "Shared with me" on OneDrive Personal ("Shared with me
     files is not supported by rclone"; reachable only through a shortcut in My files) [rclone OneDrive
     docs] → the fence never sees the boss's folders, as long as no shortcut is put inside
     GeoExpert-Backups (C7).
3. **Deletes go to the recycle bin** (rclone `hard_delete` stays at its default `false`; "Normally
   files go to the recycle bin") [rclone OneDrive docs], so a wrong delete is recoverable (C6).

What remains (accepted by Ari, R1): someone who **steals the token** from the server can use it with
any tool, outside our fence, to read, change or delete **any file in Ari's OneDrive and files shared
with him** (Microsoft's note above). The fence only protects against our own scripts' mistakes.

## 5. What `offsite_backup.sh` does (in order)

`set -euo pipefail`, `umask 077`, every message starts with `offsite:`. Settings by env with
server defaults: `BACKUP_DIR=/root/backups`, `RCLONE_CONFIG=/root/.config/rclone/rclone.conf`,
`RECIPIENTS=/root/.config/ocp/age_recipients.txt`,
`OFFSITE_KEEP_DAYS=30`, `OFFSITE_MIN_KEEP=7`, `MAX_LOCAL_AGE_H=3`, `OFFSITE_PING_URL` (from
`offsite.env`; if unset, no ping, e.g. in tests).

1. **Guards** → stop with `offsite: FAILED step=check …` (and `/fail` ping):
   - recipients file exists and has exactly the `age1…` lines (2 expected, Q4); it does **not**
     contain `AGE-SECRET-KEY` (refuses to run if someone put a private key on the server);
   - `rclone.conf` is mode 600 and its `[ocp-offsite]` section has a `root_folder_id` line (the
     folder fence, §2a; only that key is read, nothing from the file is printed);
   - **A1:** a newest local `oil_change_*.sql.gz` exists, is **not empty** (size > 0) and is
     **younger than 3 h** (else `offsite: FAILED step=check newest dump is <N> h old / empty — did
     ocp-backup run?`). With the job at 03:20 and the backup at 03:00 a good night is ~20 min old.
2. **List remote once**: `rclone lsf --files-only ocp-offsite:db` → names already there.
3. (Order note: the freshness check guards *tonight's* backup. Older local dumps still go through
   the catch-up in step 4 even though they are older than 3 h; only their content is re-checked.)
4. **For every local dump not yet on OneDrive** (oldest first, catch-up, Q3):
   - re-check the dump (`gzip -t` + "dump complete" tail) — same test as backup.sh;
   - `age -R "$RECIPIENTS" -o "$tmp" "$dump"` into a temp dir (700) that a `trap` deletes;
   - check the result starts with the line `age-encryption.org/v1` and is bigger than 0;
   - `rclone copyto "$tmp" "ocp-offsite:db/<name>.sql.gz.age"` with `--config "$RCLONE_CONFIG"`,
     `-q --retries 3 --low-level-retries 10 --contimeout 30s --timeout 5m`. rclone compares size and
     hash after upload by default — **NEEDS VERIFICATION** that OneDrive's hash is used
     (`rclone backend features ocp-offsite:` lists `QuickXorHash`);
   - **A2: verify** with `rclone lsjson` on that one file → its `Size` must equal the local `.age`
     size in bytes (`stat -c %s`), else `offsite: FAILED step=verify remote <a> bytes, local <b>
     bytes` (and `/fail` ping). The file stays on OneDrive (a later run re-uploads it, because
     `copyto` replaces a file whose size differs), but the run counts as failed and nothing is pruned.
   Plain-text dumps are **never** passed to rclone; only `.age` files.
5. **Retention, only if every upload in this run succeeded:** from the remote list, take our own names
   (`oil_change_YYYY-MM-DD_HHMMSS.sql.gz.age`), read the date **from the name** (not from the remote
   modification time), delete those older than 30 days with `rclone deletefile`, but **always keep
   the newest 7** even if old (so a long outage never empties OneDrive). Other files in the folder
   are never touched.
6. **Log one line**: `offsite: OK uploaded 1 (oil_change_2026-11-07_030000, 21K) -> ocp-offsite:db, 30 kept, 0 deleted`.
7. **Ping success** (`curl -fsS -m 10 --retry 3 "$OFFSITE_PING_URL"`). On any failure the `trap`
   sends `"$OFFSITE_PING_URL/fail"` and the script exits 1 with
   `offsite: FAILED step=<check|list|encrypt|upload|verify|prune> <short reason>`. A failed ping
   itself only adds a log line `offsite: WARNING ping failed` (the backup result does not change);
   a missing success ping makes healthchecks.io email Ari after the grace time anyway.
   The ping URL is never printed (curl runs with `-s`, the log says only "ping sent").

Never logged: the token, rclone's own debug output (`-v`/`-vv`/`--dump` are not used; `--dump
headers` would print the `Authorization: Bearer` line), file contents. rclone errors are shown only
as their last line, after a filter that drops anything with `token` or `Bearer` in it.

## 6. Timing and size

| UTC | Ulaanbaatar | What |
|---|---|---|
| 19:00 | 03:00 | `ocp-backup` makes the dump (takes seconds today) |
| **19:20** | **03:20** | **`ocp-offsite`** (new): encrypt + upload. `After=ocp-backup.service` makes it wait if the backup is still running at 19:20 |
| 19:30 | 03:30 | `ocp-messenger-cleanup` (small; overlap with offsite is harmless) |
| 00:00–04:00 | 08:00–12:00 | DigitalOcean Droplet Backup window. Our jobs are done ~4.5 h before it, so the DO snapshot already holds that night's local dump |

`Persistent=true` (Q3): if the server was off at 03:20, the job runs at boot. If the boot also
triggers the missed backup, `After=` makes offsite wait for it, so the newest dump is minutes old
and the 3 h check (A1) passes. If offsite still runs without a fresh dump, it fails with an alert,
and the next night's run uploads everything missed (catch-up).

**Size per dump: not measured yet.** Ari checks sizes only (no content):
`ls -lh /root/backups | tail -5`. Estimate until then (**ESTIMATE**, to be replaced by the real
number in the STEP 2 handoff): empty schema + destinations ≈ 10–50 KB gzipped; each service with
its reading/reminder rows adds roughly 100–300 bytes gzipped → a few hundred services a year keep a
dump **well under 1 MB**. age adds a ~200-byte header and 16 bytes per 64 KiB, i.e. nothing.
**30 copies on OneDrive ≈ 30 × (< 1 MB) < 30 MB**, a tiny part of Ari's 1 TB.

## 8. Monthly restore test (Mac) — `scripts/offsite_restore_test.sh`

   GeoExpert-Backups, pass the synced `.age` file's path (it is encrypted, so the synced copy is
   fine). The file is copied into `mktemp -d` (700) before anything else.
2. **Refuse unsafe places:** the temp dir must not be inside `~/Library/CloudStorage` or any OneDrive
   folder (a decrypted dump there would be synced back to the cloud **in plain text**).
3. **Decrypt:** `age -d -i "$KEY" file.age > dump.sql.gz` → `gzip -t` + "dump complete" check.
4. **Throw-away Postgres:** `docker run -d --rm --name ocp-restore-<random> --tmpfs
   /var/lib/postgresql/data -e POSTGRES_PASSWORD=<random> postgres:16` (same major as prod; **no**
   `-p`, so no port is opened) → wait for `pg_isready` → `gunzip -c | docker exec -i … psql -X -q -v
   ON_ERROR_STOP=1`.
5. **Count:** rows per table in the dump (`dump_row_counts.awk`) vs `count(*)` in the container.
   Print **only** `table  in_dump  restored  OK/DIFFERENT`, plus the dump's date and its age in days.
   If the Mac rclone remote was used, also print the top-level names of `ocp-offsite:` (should be
   only `db`, later `photos`; R14).
6. **Clean up (trap, also on Ctrl+C / error):** `docker rm -f` the container (tmpfs → data gone),
   delete the temp dir (encrypted + decrypted files). Exit 0 = all tables match, 1 = otherwise.

Pass rule: exit 0 **and** the dump is ≤ 2 days old (proves the nightly upload works, not just an old
file). Result goes in the handoff / PROJECT_STATE by the PM.

## 9. Photos later (9.2 / 9.2b)

Photos (9.2) will live in a Docker volume, kept 12 months. They do **not** go into the pg_dump
(the DB keeps only the link). 9.2b would extend the same job, not add a new tool:

- Second step in `offsite_backup.sh` (or `offsite_photos.sh`, same timer): for each photo file not
  on OneDrive yet, `age -R` → `ocp-offsite:photos/<YYYY-MM>/<name>.jpg.age` (inside GeoExpert-Backups, same fence) (one encrypted file per
  photo, so each night uploads only the new ones; same recipients file, same token, same ping).
- Retention mirrors D-132: delete remote photos older than 12 months (by month folder).
- Space: at 1600 px / JPEG q80 a photo is roughly 200–400 KB (**ESTIMATE**; 9.2 measures it) →
  ~0.2–0.4 GB per 1000 photos. Ari's 1 TB is enough for years; this space is shared with Ari's
  own files, so 9.2b reports the folder size (`rclone size ocp-offsite:`).
- Restoring photos needs no Postgres: decrypt and copy back into the volume. The monthly test can
  decrypt one random photo and check it opens.

## 10. Tests for CI (no network, no real secrets)

`tests/test_offsite.py`, same pattern as `tests/test_backup.py`: real bash script, fake `rclone`,
`age` and `curl` first on PATH that record their arguments in a temp dir and act on `FAKE_MODE`.
The fake `age` writes `age-encryption.org/v1` + the input reversed, so tests can tell encrypted
from plain. A fake `rclone.conf` with a dummy token string `FAKE-TOKEN-123` (no real format, so
gitleaks stays quiet).

| Test | Checks |
|---|---|
