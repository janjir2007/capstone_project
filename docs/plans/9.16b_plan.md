## 0. Short answer

1. **Three new columns on `service_records`** (migration **013**, still free: 012 is the newest file, 9.2 is not
   built): `price_mnt`, `paid_at`, `marked_unpaid_at`. There is also a fourth column, `payment_tracked`, so that
   services saved **before** 9.16b do not all turn into «Авлага» the day after deploy (§1.3).
2. **One rule, in one place** (`src/api/payments.py`, new function `manual_status`): Төлсөн = `paid_at` set;
   Авлага = «Авлага» pressed, or saved more than `PAYMENT_DUE_HOURS` (24) hours ago and not paid; otherwise
   Хүлээгдэж байна. Computed on every read from `created_at` and the current time (no timer, no nightly job).
3. **D-133 is left alone.** `ARTLAB_UNPAID_LOOKBACK_DAYS` (90 days) means "how far back the Artlab sync re-checks
   bills". The 24 h rule means something else, so it gets its **own new setting `PAYMENT_DUE_HOURS`** (default
   24). The "rename unpaid lookback setting (D-133)" item stays on the Later list.
4. **Reuse the existing `payment_status` field** of ServiceOut and the 9.6b-5 UI pieces (pill, «Төлбөр»
   filter, money format). Since Artlab is off, the field now comes from our own columns. Values: `paid` /
   `unpaid` / **`pending`** (new); `null` = not tracked. The 008/009 Artlab tables and the Artlab sync are not
   changed.
5. **API:** `POST /services` takes `price_mnt`; new `POST /services/{id}/payment` with `action` = `paid` | `unpaid`
   | `undo_paid`; new `GET /payments/receivables` for the dashboard. Contract **v0.22**.
6. **No Artlab call, no timer, no new container.** Deploy = backup → pull → build → `scripts.migrate` (013) → up.

## 1. Data: migration 013

### 1.1 `013_service_payment.up.sql`

```sql
ALTER TABLE service_records
    ADD COLUMN price_mnt        INTEGER     CHECK (price_mnt >= 0),
    ADD COLUMN paid_at          TIMESTAMPTZ,
    ADD COLUMN marked_unpaid_at TIMESTAMPTZ,
    -- false = saved before 9.16b: no payment status at all (shown as before, never «Авлага»)
    ADD COLUMN payment_tracked  BOOLEAN     NOT NULL DEFAULT false;

-- Every service saved from now on is tracked; the rows that already exist keep false.
ALTER TABLE service_records ALTER COLUMN payment_tracked SET DEFAULT true;

-- Dashboard «Төлбөр» + plate-screen check read only the unpaid candidates.
CREATE INDEX service_records_not_paid_idx ON service_records (vehicle_id, created_at)
    WHERE payment_tracked AND paid_at IS NULL;
```

Notes:
- `price_mnt INTEGER`: whole tugrik, ≥ 0, NULL = no price entered. INTEGER holds up to 2 147 483 647 ₮, which
  is plenty for one oil change. `0` is allowed (a free service, e.g. warranty) and is different from NULL.
- `paid_at` / `marked_unpaid_at` are TIMESTAMPTZ (UTC in the DB, shown in Ulaanbaatar time), like `created_at`
  and `reviewed_at` (012).
- `ADD COLUMN … DEFAULT false` and then `SET DEFAULT true` gives existing rows `false` and new rows `true`.
  In Postgres 11+ this is one fast metadata change; the table is not rewritten.
- No new table: payment is always full (decision), so one service = at most one payment.
- **Proposed names:** `price_mnt` (unit in the name, like `odometer_km`), `paid_at`, `marked_unpaid_at`,
  `payment_tracked`. PM may rename them before the build.

### 1.2 `013_service_payment.down.sql`

```sql
DROP INDEX service_records_not_paid_idx;
ALTER TABLE service_records
    DROP COLUMN payment_tracked,
    DROP COLUMN marked_unpaid_at,
    DROP COLUMN paid_at,
    DROP COLUMN price_mnt;
```

DOWN **loses** every price and every «Төлсөн» / «Авлага» click. The header comment says so, and the deploy
step takes a backup first (`ocp-backup.service`, as for every DB change).

### 1.3 Why `payment_tracked` (needs PM/Ari OK)

Without it, every service saved before 9.16b (no price, `paid_at` NULL, `created_at` > 24 h ago) would be
**Авлага** on the first day: the plate screen would warn for every returning truck, and the dashboard count
would be wrong. With `payment_tracked = false` those services have `payment_status = null`: no pill, no buttons,
not counted, the same as today. Since the 11-05 demo wipe only a few real services exist, so the number of
rows affected is small. The build step prints `SELECT count(*) FROM service_records` before the migration
(a count only) so Ari can see it.

Alternative, if Ari wants the old services in the list: no flag, and Ari presses «Төлсөн» on each old one after
deploy. Not recommended (an easy-to-miss manual job and wrong warnings until it is done).

### 1.4 ORM

`src/api/models.py` `ServiceRecord`: `price_mnt: Mapped[int | None]`, `paid_at`, `marked_unpaid_at:
Mapped[datetime | None]` (timezone=True), `payment_tracked: Mapped[bool]` (server_default true). These are plain
types, so the SQLite test engines that build `Base.metadata` keep working (the reason `payments.py` uses raw
SQL for the Artlab array columns).

## 2. Status rule

### 2.1 Rule (`src/api/payments.py`, new pure function)

```python
def manual_status(tracked: bool, paid_at, marked_unpaid_at, created_at, now, due_hours) -> str | None:
    if not tracked:                      return None        # saved before 9.16b
    if paid_at is not None:              return "paid"      # «Төлсөн»
    if marked_unpaid_at is not None:     return "unpaid"    # «Авлага» pressed
    if now - created_at >= timedelta(hours=due_hours):
                                         return "unpaid"    # «Авлага» after 24 h
    return "pending"                                         # «Хүлээгдэж байна»
```

- **`now`** comes from the existing `get_now()` dependency (`src/api/clock.py`, timezone-aware UTC), so tests
  freeze it like `get_today`. Both times are timezone-aware, so the 24 h is exact whatever the server or DB
  timezone (the DB runs in UTC, Mongolia is UTC+8 with no DST). Only the **display** turns into UB time.
- **The clock starts at `created_at`** (the moment it was saved), **not `service_date`**. A service typed in
  today for yesterday (`service_date` = yesterday) still gets 24 h from saving.
- **Exactly 24 h counts as Авлага** (`>=`).
- **Price does not change the status.** A service without a price can still be Авлага (it shows «Үнэ
  оруулаагүй» instead of an amount, see §4). It is counted in the number of Авлага services but adds 0 ₮
  to the total.
- `unpaid_since` (shown as the Авлага date) = `marked_unpaid_at` if pressed, else `created_at + due_hours`.

### 2.3 Setting `PAYMENT_DUE_HOURS`

- New in `src/api/config.py`: `payment_due_hours()`, default **24**, whole number > 0, else `ConfigError`. It is
  checked at API start-up like `unpaid_lookback_days()` (`src/api/main.py`), so a typo stops the API instead of
  silently using a wrong rule.
- Optional in `.env` (not set = 24). `.env.example` + `docs/deploy.md` get one line.
- **D-133 (`ARTLAB_UNPAID_LOOKBACK_DAYS`, 90 days) is left as it is.** It is the Artlab nightly re-check
  window, measured in days, used only by `GET /payments/unpaid` and `src/artlab/sync.py`. Reusing it for a
  24-hour grace time would mix two meanings, and Artlab later still needs its own window.

## 3. API changes (contract v0.21 → **v0.22**)

### 3.1 ServiceOut (everywhere a service appears: card `last_service` / `history`, lookup cards, search rows,
`POST /services` answer)

| Field | Change |
|---|---|
| `payment_status` | **meaning change**: now from our own columns: `paid` «Төлсөн» · `unpaid` «Авлага» · `pending` «Хүлээгдэж байна» (new value) · `null` = not tracked (saved before 9.16b). `paid_later` / `unknown` stay in the type for a later Artlab fill but are not produced. Also filled in the `POST /services` answer (`pending`) |
| `amount_due` | = `price_mnt` when `payment_status = unpaid`, else null (was: Artlab credit) |
| `match_confidence` | unchanged type; always null (Artlab off) |
| `price_mnt` | **new**, int \| null |
| `paid_at` | **new**, datetime with offset \| null |
| `marked_unpaid_at` | **new**, datetime with offset \| null |
| `unpaid_since` | **new**, datetime \| null: when it became Авлага (§2.1); only when `unpaid` |

Code: `service_out()` in `src/api/routers/vehicles.py` takes the status from `manual_status(...)` instead of
`payment_of(...)`. `connected()` / `service_payments()` / `payment_of()` stay in `payments.py` (unused by
ServiceOut, kept for Artlab) — §6.

### 3.2 `POST /services` — new optional body field

`price_mnt`: int ≥ 0, optional (`Field(default=None, ge=0, le=100_000_000)`). The upper limit catches a typo of
extra zeros: 100 000 000 → 422 «Үнэ хэт их байна». A decimal or negative number → 422. The answer's
`service.payment_status` = `pending`.

### 3.3 `POST /services/{id}/payment` — new (the only payment write)

Body `{"action": "paid" | "unpaid" | "undo_paid"}` (extra="forbid"). Answer **200** = the updated ServiceOut.

| action | Button | What it does | Idempotent |
|---|---|---|---|
| `paid` | «Төлсөн» | `paid_at = now` if it is null (keeps `marked_unpaid_at` as history) | second call = no change, 200 |
| `unpaid` | «Авлага» | `marked_unpaid_at = now` if null; **and** `paid_at = null` (a paid one marked Авлага is a correction) | yes |
| `undo_paid` | «Буцаах» (under Төлсөн) | `paid_at = null` → the rule decides again (pending or Авлага) | yes |

Errors: **404** unknown service · **409** `payment_tracked = false` («Энэ үйлчилгээ төлбөрийн бүртгэлээс
өмнөх») · **422** other action. Any service can be changed, not only the newest one: the plate screen pays an
**older** unpaid service (§4.2). Like every data route it is behind the login (Caddy does not make it public).
No user name is stored (one shared password, D-117).

### 3.4 `GET /payments/receivables` — new, read only (dashboard «Төлбөр»)

```json
{
  "due_hours": 24,
  "total_mnt": 340000,          // sum of price_mnt of every Авлага service (no price = 0)
  "count": 6,                   // Авлага services, with or without price
  "count_no_price": 1,
  "trucks": [                   // one row per truck, biggest amount first, then oldest
    {"vehicle_id": 12, "identifier": "1234 УБА", "company_name": "Говь Тээвэр ХХК",
     "services": 2, "amount_mnt": 160000, "oldest_service_date": "2026-11-12",
     "oldest_unpaid_since": "2026-11-13T10:00:00+08:00", "driver_phone": "99112233",
     "service_ids": [41, 57]}
  ]
}
```

One SQL query over `service_records WHERE payment_tracked AND paid_at IS NULL` (the partial index), with the
rule applied in Python with the same `manual_status` (one implementation, so no copy of the rule in SQL).
`driver_phone` = from the newest Авлага service; shown on screen only, **never in Excel** (same rule as 9.6b-5).
`GET /payments/unpaid` (Artlab) is not changed.

### 3.5 `GET /vehicles/search?payment_status=` (exists since v0.16)

Now filters on the manual status; `pending` is accepted. Excel uses `with_services=true`, so each service row
already carries `price_mnt` + `payment_status`.

> (**meaning change**, + `pending`), `amount_due` = price when Авлага; new `price_mnt`, `paid_at`,

### 4.2 Plate screen (`record.py` step `result`, the hidden `rec_unpaid` box from 9.16a)

- Content (orange warning style, like `rec-banner warn`):
  - **«Өмнөх үйлчилгээ (2026-11-12) төлөгдөөгүй»** + «80 000₮» (or «Үнэ оруулаагүй»). If there are more than

  - Button **«Үргэлжлүүлэх»** → hides the box for this plate in this session (`rec_unpaid_dismissed`); nothing

- CSS: the 9.16a rule in `common.py` that hides `.st-key-rec_unpaid` is replaced by "hidden when empty". Only

## 9. Risks

| Risk | Mitigation |
|---|---|
| R1. Old services all turn «Авлага» after deploy | `payment_tracked = false` for existing rows (§1.3) |
| R2. Wrong button tap marks a debt paid | «Буцаах» with a confirm; «Авлага» can turn into «Төлсөн» again; all state is two timestamps, easy to fix |
| R3. Price typo (extra zero) inflates the dashboard total | API upper limit 100 000 000 ₮; amount shown on the success screen and the card. No edit of price after saving in 9.16b (§10 Q2) |
| R4. Many services saved without a price → «Төлбөр» ₮ total too low | count and «N нь үнэгүй» shown next to the total, so the total is not read as the full debt |
| R5. Meaning change of `payment_status` breaks a client | Only our own UI reads it; Artlab is not connected, so today the field is always null. Written in the contract as a meaning change |
| R6. A driver pays later but nobody presses «Төлсөн» → wrong warning on the next visit | The warning itself is the reminder: «Төлсөн» is one tap on the plate screen |
| R7. Shared password: no record of who pressed | Accepted (D-117); timestamps are kept. Later: per-user login |
| R8. Plate screen extra work on a slow phone | No extra call: the warning uses the lookup already made for the status |
| R9. Artlab later sets `paid_at` and conflicts with a manual click | Out of scope; when built, Artlab only fills an empty `paid_at` and a `paid_source` column is added |
| R10. Server clock wrong | Same as every timestamp today (`created_at` uses DB `now()`, the rule uses API `now`, both on one host). Both are UTC-aware |
| R11. Phones on the «Төлбөр» list | On screen only, never in Excel (same as 9.6b-5, RISK-06 accepted) |
